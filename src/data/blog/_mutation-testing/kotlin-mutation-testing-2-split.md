## Table of contents

[지난 글](/kotlin-mutation-testing-1-split)에서 뮤테이션 테스트와 기존 도구를 정리했다. Kotlin에서는 PIT와 Arcmutate 조합이 가장 현실적인 선택이지만, Stryker처럼 소스를 직접 변형하는 도구는 아직 베타 단계의 프로젝트 정도만 있다. 그래서 Kotlin용 Stryker 스타일 도구를 직접 만들어 보기로 했고, 만드는 과정을 단계마다 글로 남기려 한다.

이 글은 그 계획이다. **아직 코드는 한 줄도 쓰지 않았다.** 정해진 건 어떤 방식으로 만들지, 첫 버전에 무엇을 넣고 뺄지, 어떤 순서로 진행할지까지다. 만들면서 계획이 바뀌면 그 글에서 바뀐 이유를 적는다.

# 바이트코드를 바꿀까, 소스를 바꿀까

도구를 직접 만든다면 가장 먼저 정할 것이 변형 대상이다. PIT와 Stryker의 차이도 대부분 여기서 나온다.

| | 바이트코드 변형 | 소스 변형 |
| --- | --- | --- |
| 실행 속도 | 재컴파일이 없어 빠르다 | 컴파일이 필요해 느리다. schemata로 보완해야 한다 |
| 컴파일 에러 뮤턴트 | 없다 | 생긴다. 걸러내는 장치가 필요하다 |
| 언어 지원 | 구현 하나로 JVM 언어 전체 | 언어마다 따로 구현 |
| 따라가야 할 변화 | 컴파일러의 코드 생성 패턴 (포맷 자체는 안정적) | 언어 문법 |
| 컴파일러 생성 코드 | 같이 변형된다 (junk mutant) | 구조적으로 건드리지 않는다 |
| 위치 정보 | 줄 단위. 열 정보가 없다 | 줄과 열, 원본과 변경의 diff |
| 뮤턴트 모양 | 소스 연산자와 1:1로 대응하지 않을 때가 있다 | 개발자가 실제로 낼 법한 실수 |
| 언어 고유 연산자 | 표현하기 어렵다 | 만들 수 있다 |

Kotlin에서는 바이트코드 쪽 단점이 특히 크다. 고수준 문법이 바이트코드로 내려가면서 흩어지기 때문이다.

- `x?.length`는 null 분기 하나가 된다. "safe call을 non-null 단언으로 바꾼다" 같은 뮤턴트를 표현할 단위가 없다
- `x in 1..10`은 비교 두 번이 된다
- 객체 `==`는 `Intrinsics.areEqual` 호출이 된다
- `when`은 경우에 따라 `tableswitch`가 된다
- 컴파일러가 조건을 뒤집어서 분기를 만든다. `if (a >= b)`가 "a < b면 else로 점프"로 컴파일되니, 바이트코드에서 바꾼 연산자를 소스 연산자로 다시 풀어 설명해야 한다
- inline 함수는 본문이 호출한 쪽에 복사되면서 줄 번호 매핑이 꼬인다

반대로 소스를 변형하면 Kotlin 개발자가 실제로 저지르는 실수를 그대로 뮤턴트로 만들 수 있다. `?.`를 `!!`로, `?:`의 우변을 제거, `1..10`을 `1 until 10`으로, `listOf(...)`를 `emptyList()`로. 바이트코드에서는 만들기 어려운 뮤턴트다.

## 절충안: 컴파일러 플러그인

Kotlin 컴파일러 플러그인으로 IR 단계에서 변형하는 방법도 있다. 타입 체크가 끝난 뒤라 컴파일 에러 뮤턴트가 거의 없고, 바이트코드보다 소스 구조가 많이 남아 있다. 하지만 IR API는 안정된 공개 API가 아니어서 K2 전환처럼 컴파일러가 크게 바뀔 때마다 플러그인을 고쳐야 한다. [지난 글](/kotlin-mutation-testing-1-split)에서 본 mutflow도 릴리스마다 빌드할 때 쓴 Kotlin 버전을 요구하고, Kotlin 버전이 맞지 않으면 알아보기 어려운 컴파일러 에러가 난다고 README에 적혀 있다. 혼자 유지보수하기에는 부담이 가장 큰 선택지다.

## 소스 변형으로 정했다

바이트코드 방식은 PIT와 Arcmutate가 이미 잘 하고 있다. "Kotlin용 Stryker"를 만들 이유가 있다면 그건 소스 변형의 장점에서 나온다. junk mutant가 없는 리포트, 소스 위치와 diff로 읽히는 리포트, Kotlin 고유 연산자. 대신 소스 변형의 단점인 속도와 컴파일 에러를 떠안는다.

mutflow도 컴파일을 한 번만 한다는 점에서는 Stryker와 같은 방향이다. 하지만 만들려는 도구와는 세 가지가 다르다. mutflow는 IR을 변형하고, 테스트 코드에 어노테이션과 `MutFlow.underTest { }` 블록을 넣어야 돌아가며, 결과를 테스트 실행 요약과 마크다운으로 낸다. 만들려는 도구는 소스를 변형하고, 테스트 코드를 고치지 않고 프로젝트 밖에서 독립 실행하며, Stryker의 리포트 스키마로 결과를 낸다. IR 방식은 Kotlin 버전을 계속 따라가야 하는데, 그 길은 mutflow가 이미 가고 있으니 혼자 다시 갈 이유도 약하다.

# 직접 만들면 어디가 어려운가

## 생각보다 쉬운 부분

**파싱**은 이미 있는 걸 쓴다. Kotlin 컴파일러가 쓰는 PSI를 `kotlin-compiler-embeddable`로 가져오거나, tree-sitter-kotlin을 쓰면 된다.

**연산자**는 트리에서 노드를 찾아 텍스트 범위를 바꾸는 일이다. 연산자 하나가 수십 줄이면 된다.

**리포트**는 만들 필요가 거의 없다. `mutation-testing-elements` 스키마에 맞는 JSON만 내면 Stryker의 HTML 리포트를 그대로 쓸 수 있다.

## 어려운 부분 1: schemata와 Kotlin 타입 시스템

소스 변형이 쓸 만한 속도를 내려면 schemata가 필요하다. 그런데 Kotlin에서는 뮤턴트를 런타임 스위치로 감싸는 순간 컴파일이 깨지는 자리가 많다.

```kotlin
// 원본
if (x != null && x.length > 3) { ... }

// schemata 적용 후
if ((if (Mutant.id == 1) x == null else x != null) && x.length > 3) { ... }
// 컴파일 에러: x.length에서 x가 String?로 남는다
```

원본에서는 `x != null`을 지나면 스마트 캐스트로 `x`가 `String`이 된다. 조건을 `if` 식으로 감싸면 컴파일러가 그 흐름을 따라가지 못해 스마트 캐스트가 사라진다. 뮤턴트를 켜지 않은 원래 경로까지 컴파일이 안 된다.

런타임 스위치를 아예 넣을 수 없는 자리도 있다. `const val` 초기값, 어노테이션 인자, `when`의 분기 상수와 exhaustive 검사, `inline`/`reified` 함수, `suspend` 경계. 결국 "컴파일하고, 에러 위치를 뮤턴트에 매핑하고, 그 뮤턴트를 빼고, 다시 컴파일"하는 루프가 필요하다.

## 어려운 부분 2: 테스트 실행

뮤턴트마다 `./gradlew test`를 부르면 Gradle 구성 단계부터 매번 다시 지나간다. 빨라지려면 JUnit Platform Launcher로 JVM 하나를 재사용하면서 테스트를 직접 돌려야 하고, 뮤턴트마다 관련 테스트만 고르려면 테스트별 커버리지가 필요하다. JVM을 재사용하면 static 상태가 다음 뮤턴트로 새기 때문에 클래스로더를 분리하거나 워커를 주기적으로 재시작해야 한다. 무한 루프에 빠진 뮤턴트를 끊을 타임아웃도 있어야 한다.

## 규모

혼자 만든다고 보고 추정해 봤다. 동작만 확인하는 PoC는 1~3주, 쓸 만한 MVP는 2~3개월, 실무 수준은 6개월 이상. 그리고 가장 큰 리스크는 기능 구현이 아니라 Kotlin 컴파일러 버전을 계속 따라가는 부담이다.

팀에서 쓸 도구로만 보면 PIT와 Arcmutate 조합이 비용 대비 낫다. 그래도 만들어 보기로 한 건 학습과 사이드 프로젝트로서 좋은 주제라서다. **컴파일러 프런트엔드, 테스트 러너, 빌드 도구를 한 프로젝트에서 전부 건드려 볼 수 있다.** 이런 주제는 흔하지 않다.

# 첫 번째 버전: 끝까지 연결하기

첫 버전의 목표는 속도가 아니다. **프로젝트를 넣으면 뮤턴트를 만들고, 테스트를 돌리고, Stryker 스타일 리포트가 나오는 데까지** 파이프라인 전체를 먼저 잇는다. 어느 단계가 실제로 느리고 어디서 컴파일이 깨지는지는 돌려 봐야 안다.

| 영역 | 이번 버전 | 다음으로 미룬 것 |
| --- | --- | --- |
| 대상 프로젝트 | 단일 모듈 Kotlin/JVM Gradle, JUnit 5와 Kotest | 멀티모듈, Android |
| 파싱 | PSI (`kotlin-compiler-embeddable`) | |
| 연산자 | 타입이 바뀌지 않는 6개 | 반환값 변경, 호출 제거 |
| 뮤턴트 적용 | 하나씩 적용, 테스트, 원복 | schemata |
| 테스트 선택 | 매번 전체 테스트 | 테스트별 커버리지 |
| 실행 | Gradle Tooling API, 순차 실행 | 병렬 실행 |
| 분석 범위 | 프로젝트 전체 | 증분 분석, git 연동 |
| 판정 | Killed, Survived, CompileError, Timeout | |
| 리포트 | `mutation-testing-elements` JSON과 HTML, 콘솔 스코어 | |
| 사용 방식 | CLI (`list`, `run`, `--threshold`) | Gradle 플러그인 |

## 왜 이렇게 골랐나

**연산자는 같은 타입의 식끼리 바꾸는 것만 골랐다.**

- ConditionalBoundary: `<` ↔ `<=`, `>` ↔ `>=`
- NegateConditional: `==` ↔ `!=`, `<` ↔ `>=` 등
- Arithmetic: `+` ↔ `-`, `*` ↔ `/`
- BooleanLiteral: `true` ↔ `false`
- LogicalOperator: `&&` ↔ `||`
- RemoveNot: `!x` → `x`

반환값 변경은 non-null 반환 타입에 `null`을 넣으면 깨지고, 호출 제거는 호출 결과를 쓰는 자리에서 깨진다. 타입이 같아도 연산자 오버로딩(`String`의 `+`)이나 null 체크 반전처럼 깨지는 경우는 남는데, 그 비율이 얼마나 되는지는 4단계에서 잰다.

**테스트 프레임워크는 JUnit 5와 Kotest를 둘 다 받는다.** Kotlin 프로젝트에서는 둘을 함께 쓰는 경우가 흔하고, 우리 팀도 주로 Kotest를 쓴다. Kotest는 `kotest-runner-junit5`로 JUnit Platform 위에서 도는 테스트 엔진이다. 첫 버전은 뮤턴트마다 Gradle test 태스크(`useJUnitPlatform()` 설정 전제)를 통째로 돌리고 결과만 보니, 어느 프레임워크로 쓴 테스트인지 구분할 필요가 없다. 추가 비용이 거의 없다.

어려워지는 건 테스트별 커버리지로 관련 테스트만 고르는 단계다. Kotest 테스트는 메서드가 아니라 람다 DSL이라 실행 전에는 구조가 보이지 않고, 개별 테스트를 중첩된 이름 경로로 식별하며, `withData` 같은 동적 테스트는 런타임에 생긴다. PIT도 그래서 Kotest용 `pitest-kotest` 플러그인을 따로 둔다. 그 단계는 클래스와 메서드가 아니라 JUnit Platform의 테스트 식별자(UniqueId)를 기준으로 설계해서 두 프레임워크를 함께 다룰 생각이다.

**뮤턴트는 하나씩 적용한다.** schemata를 쓰지 않으면 앞에서 본 스마트 캐스트 문제가 원본 경로를 깨뜨리지 않는다. 뮤턴트 자체가 컴파일되지 않는 경우(예: `x != null`을 `x == null`로 바꾸면 뒤의 `x.length`가 깨진다)는 그 뮤턴트 하나만 CompileError로 기록하고 넘어가면 된다. 빌드 전체가 멈추지 않는다.

**느린 건 일부러 감수한다.** 뮤턴트 하나에 컴파일과 전체 테스트가 한 번씩 붙으니 느릴 수밖에 없다. 하지만 schemata, 테스트별 커버리지, 병렬 실행 중 무엇이 가장 효과가 클지는 실제 프로젝트에서 시간을 재 봐야 고를 수 있다.

**실행은 Gradle Tooling API로 한다.** CLI로 `./gradlew`를 매번 띄우는 것보다 데몬을 재사용해서 빠르고, 실행 중인 빌드를 취소할 수 있어서 타임아웃을 깔끔하게 처리할 수 있다. JUnit Platform Launcher를 직접 다루는 건 그다음 문제다.

**파싱은 PSI로 한다.** 컴파일러가 쓰는 파서라 Kotlin 문법을 빠짐없이 정확하게 읽는다. IDE 밖에서 PSI 환경을 띄우는 구성이 번거롭다고 알려져 있어서, 0단계에서 먼저 검증하고 막히면 tree-sitter-kotlin으로 바꾼다.

**리포트는 공개 스키마를 쓴다.** JSON만 맞추면 Stryker의 HTML 리포트가 그대로 동작하니 UI를 만들 필요가 없다. 소스 기준 diff를 보여주는 리포트는 소스 변형을 고른 이유이기도 하다.

## 기술 스택과 구조

Kotlin(JVM)으로 만든다. 파싱은 `kotlin-compiler-embeddable`, 실행은 Gradle Tooling API, CLI는 Clikt, JSON은 kotlinx.serialization이다. 검증용 프로젝트의 테스트는 Kotest(`kotest-runner-junit5`)와 JUnit 5로 쓴다.

```
kmutate/
├── kmutate-core/
│   └── src/main/kotlin/
│       ├── parse/      # PSI로 소스 읽기
│       ├── mutator/    # 연산자, 뮤턴트 탐색
│       ├── runner/     # 적용, 실행, 판정
│       ├── report/     # JSON, HTML, 콘솔 출력
│       └── cli/        # list, run 명령
└── sample-target/      # 일부러 허술한 테스트를 넣은 검증용 프로젝트
```

`kmutate`는 가칭이다.

`sample-target`은 인수 테스트 역할을 한다. 테스트는 Kotest 스펙을 기본으로 쓰고 JUnit 5 테스트를 섞는다. 두 프레임워크 양쪽에 지난 글의 `isAdult`처럼 경계값을 빠뜨린 테스트를 일부러 넣어 두고, **어떤 뮤턴트가 살아남아야 하는지 목록을 미리 정해 둔다.** 도구의 결과가 그 목록과 같으면 맞게 동작한다고 본다.

## 진행 순서

0. **셋업** (반나절): 멀티프로젝트 구조와 `sample-target`을 만들고, PSI로 파일 하나를 읽어 본다. 완료 기준은 `sample-target`의 테스트가 통과하고 PSI 트리가 출력되는 것.
1. **파싱과 뮤턴트 탐색** (1~2일): 연산자 6개를 구현한다. 완료 기준은 `kmutate list`가 `sample-target`의 뮤턴트를 파일, 줄, 열, 원본과 변경 코드로 출력하는 것.
2. **적용과 실행** (2~3일): 뮤턴트를 적용하고 Tooling API로 테스트를 돌려 판정한다. 뮤턴트 없이 한 번 돌리는 베이스라인 실행으로 테스트가 원래 통과하는지 확인하고, 그 시간으로 타임아웃(베이스라인 × 1.5 + 5초)을 정한다. 완료 기준은 `kmutate run`의 Survived 목록이 미리 정한 기대 목록과 같고, 실행 뒤에도 원본 소스가 바뀌지 않는 것.
3. **리포트** (1일): `mutation-testing-elements` JSON과 HTML, 콘솔 스코어를 낸다. 완료 기준은 HTML 리포트에서 생존 뮤턴트의 diff가 보이고, 스코어가 `--threshold`보다 낮으면 0이 아닌 종료 코드로 끝나는 것.
4. **측정** (반나절): 실제 프로젝트에 돌려서 뮤턴트 수, 전체 소요 시간, CompileError 비율을 잰다. 완료 기준은 이 숫자로 다음 단계의 우선순위를 정하는 것.

전부 합쳐 1~1.5주로 잡았다.

## 미리 보이는 리스크

- **PSI 단독 환경 구성**: 0단계에서 가장 먼저 검증한다. 막히면 tree-sitter-kotlin으로 바꾼다
- **느린 실행**: 첫 버전에서는 감수한다. 4단계에서 잰 숫자로 개선 순서를 정한다
- **원본 오염**: 뮤턴트를 적용하다 중간에 죽으면 원본 소스가 바뀐 채로 남는다. 대상 프로젝트를 임시 디렉터리에 복사해서 그 복사본에서만 작업한다
- **Gradle 증분 빌드와 캐시**: 테스트 태스크가 최신 상태로 판단돼 건너뛰어지면 실패 없이 끝나서 Survived로 잘못 판정된다. 테스트 태스크는 매번 다시 실행되게 하고, 실제로 실행된 테스트 수를 확인한다

다음 글은 0~1단계, 셋업과 파싱, 뮤턴트 탐색을 구현한 기록이 된다.
