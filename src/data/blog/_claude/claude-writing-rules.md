## Table of contents

Claude에게 설계 문서를 맡기면 결과물이 꽤 그럴듯하게 나온다. 구조도 잡혀 있고 빠진 항목도 별로 없다. 그런데 읽다 보면 어느 순간 화면을 훑고 있다. 분량은 세 페이지인데 실제로 판단에 필요한 내용은 한 문단이다.

주석도 비슷하다. 메서드 하나에 JavaDoc이 열두 줄씩 붙는데, 그중 여덟 줄은 시그니처를 한국어로 옮겨 적은 것이다.

"좀 더 간결하게 써줘"라고 하면 그 턴에서는 줄어든다. 다음 세션에서는 원래대로 돌아온다. 이건 프롬프트로 매번 고칠 문제가 아니라 **규칙으로 박아둘 문제**였다. 그래서 `CLAUDE.md`에 넣은 내용을 정리해본다.

# 왜 길어지고 왜 어색한가

원인은 두 가지로 나뉜다. 섞어서 다루면 규칙이 애매해지니 분리해서 봤다.

**장황함은 친절함의 부작용이다.** 모델은 빠뜨리는 쪽보다 더 쓰는 쪽을 안전하게 여긴다. 그래서 섹션을 시작하기 전에 이 섹션이 무엇을 다룰지 예고하고, 본문을 쓰고, 맺음말에서 다시 요약한다. 같은 사실이 세 번 나온다. 사람이 쓴 문서라면 성의로 읽히겠지만, 읽는 사람 입장에서는 필요한 한 문장을 찾는 시간이 세 배가 된다.

**번역투는 어순의 문제다.** 영어 문장 구조가 한국어 표면에 그대로 남으면 "~하는 것이 가능하다", "~를 수행하도록 한다" 같은 문장이 나온다. 뜻은 통하는데 주어가 흐려지고 길이가 늘어난다. 여기에 피동과 `~적(的)`이 붙으면 누가 무엇을 하는지가 문장에서 사라진다. "Config 룰에 의해 자동적으로 탐지되어진다" 같은 문장은 정보량이 "Config 룰이 탐지한다"와 같다.

# 규칙은 취향이 아니라 판정 가능한 형태로

처음에는 이렇게 썼다.

```markdown
문서는 간결하게 쓴다. 번역투를 피하고 자연스러운 한국어로 작성한다.
```

거의 효과가 없었다. "간결"과 "자연스러움"은 모델이 자기 기준으로 해석한다. 이미 자기 딴에는 간결하게 쓰고 있었으니 바뀔 이유가 없다.

지시를 **지켰는지 아닌지 기계적으로 판정할 수 있는 형태**로 바꾸고 나서 달라졌다. 네 가지 방식을 썼다.

- **금지 목록**: 쓰지 말 것을 이름으로 지목한다
- **치환표**: 금지한 표현을 무엇으로 바꿀지 짝으로 준다
- **수치 상한**: 줄 수, 글자 수처럼 셀 수 있는 한계를 준다
- **나쁨/좋음 쌍**: 같은 내용을 두 버전으로 보여준다

특히 마지막이 중요하다. 규칙 열 줄보다 나쁜 예시 하나와 좋은 예시 하나가 더 정확하게 전달된다. 설명으로는 재현되지 않던 문체가 예시를 붙이면 재현된다.

# 표기와 문장 규칙

`CLAUDE.md` 상단에 문장 단위 규칙을 두고, 문서/주석/커밋 메시지가 전부 이걸 참조하게 했다.

## 엠 대시 금지

```markdown
**엠 대시(`—`)와 엔 대시(`–`)를 쓰지 않는다.** 한국어에서 흔히 쓰는 기호가 아니라
읽는 흐름을 끊는다. 문서, 코드 주석, 로그 메시지, 커밋 메시지, PR 본문 모두 해당한다.

대신 쉼표, 콜론(`:`), 괄호, 하이픈(`-`), 또는 문장 분리로 표현한다.

- `ClickUp-Task는 필수 — 누락 시 hook이 거부한다`
  -> `ClickUp-Task는 필수다. 누락 시 hook이 거부한다`
```

사소해 보이지만 AI가 쓴 글의 표식처럼 되어 있는 기호다. 한국어 문서에서는 특히 튄다. **적용 범위를 문서에 한정하지 않은 것**이 포인트다. 문서만 막으면 커밋 메시지와 로그 메시지에서 그대로 나온다.

## 번역투 치환표

목록으로 나열하는 대신 표로 짝을 지었다.

| 번역투 | 우리말 |
| --- | --- |
| ~를 가지고 있다 | ~가 있다 |
| ~하는 것이 가능하다 | ~할 수 있다 |
| ~할 필요가 있다 | ~해야 한다 |
| ~할 수 있도록 하기 위하여 | ~하려고, ~하기 위해 |
| ~하는 것으로 판단된다 | ~한다, ~로 보인다 |
| ~를 수행하도록 한다 | ~한다 |
| ~를 통하여 | ~로, ~으로 |
| ~에 대하여 검토한다 | ~를 검토한다 |
| ~에 있어서 | ~에서, ~은 |
| ~중의 하나이다 | ~다 |
| 항목들, 룰들 | 항목, 룰 |
| 기본적으로, 일반적으로, 사실상 | (뜻이 안 바뀌면 삭제) |

마지막 줄이 의외로 많이 걸린다. "기본적으로", "일반적으로", "사실상"은 문장에서 빼도 뜻이 그대로인 경우가 대부분인데, 습관처럼 붙는다. **뺐을 때 뜻이 바뀌는지**를 판정 기준으로 준 덕분에 모델이 스스로 거를 수 있게 됐다.

그리고 표에 담기 어려운 세 가지를 따로 적었다.

```markdown
- **피동을 남발하지 않는다.** "Config 룰에 의해 탐지된다" -> "Config 룰이 탐지한다".
  행위자를 모를 때만 피동을 쓴다
- **이중피동은 쓰지 않는다.** "보여진다", "되어진다" -> "보인다", "된다"
- **`~적(的)`을 붙여 뜻을 흐리지 않는다.** "자동적으로 처리된다" -> "자동으로 처리한다"
```

# 문서 작성 규칙

문장 규칙만으로는 분량이 안 줄었다. 문장 하나하나는 짧아졌는데 문단 수가 그대로였다. 구조 차원의 규칙이 따로 필요했다.

## 중복을 줄인다

장황함의 대부분은 **같은 말을 여러 형태로 반복하는 것**이었다. 그래서 반복이 나타나는 자리를 하나씩 지목했다.

```markdown
- **같은 사실을 두 곳에 쓰지 않는다.** 한 곳에 쓰고 나머지는 참조한다.
  양쪽에 쓰면 한쪽만 고쳐져서 문서가 스스로와 어긋난다
- 섹션 도입부에 그 섹션이 무엇을 다루는지 예고하지 않는다. 제목이 한다
- 맺음말에서 본문을 다시 요약하지 않는다
- "즉", "다시 말해"로 앞 문단을 바꿔 말하지 않는다. 앞 문단이 안 통했으면 앞 문단을 고친다
- 첫머리 요약은 본문과 층위가 다를 때만 둔다. 본문을 줄여 놓은 것이면 뺀다
```

"섹션 도입부에 예고하지 않는다. 제목이 한다"는 한 줄이 체감상 가장 효과가 컸다. `## 4.3 리전 위반 탐지` 아래에 "이 섹션에서는 리전 위반 탐지에 대해 설명한다"가 붙는 패턴이 사라졌다.

## 히스토리를 쓰지 않는다

두 번째로 큰 분량 증가 요인은 경위 서술이었다. 대화 중에 "처음엔 A로 하려다 B로 바꾸자"고 정하면, 문서에 그 과정이 그대로 들어간다.

```markdown
**지금 상태를 쓴다.** 어떤 경위로 그렇게 됐는지는 커밋 메시지와 ADR이 답한다.
"초기에는 A였으나 B로 바꿨다"는 대개 지울 문장이다. 독자는 B만 알면 된다.

예외는 둘뿐이다.

- 경위를 모르면 유지보수자가 되돌릴 위험이 있는 결정
- 사용자가 이력을 명시적으로 요청한 경우 (회고, 인수인계 문서)
```

여기서 **예외를 명시한 것**이 중요하다. 예외 없이 "히스토리 금지"라고만 쓰면, 남겨야 할 결정 배경까지 지워버린다. 금지 규칙을 줄 때는 금지가 풀리는 조건을 같이 주는 편이 안전했다.

## 문장 중간에서 줄을 바꾸지 않는다

문체와는 별개인데, diff 품질 때문에 넣은 규칙이다.

```markdown
**줄바꿈은 문장이 끝난 자리에서만 한다.** 화면 너비를 맞추려고 문장을 접지 않는다.

단어 하나를 고쳐도 뒤따르는 줄이 전부 다시 접힌다. diff가 실제 변경보다 커지고,
리뷰에서 무엇이 바뀌었는지 묻힌다.
```

모델은 80자쯤에서 문장을 접는 습관이 있다. 마크다운에서는 단어 하나만 고쳐도 문단 전체가 다시 접히면서 diff가 벌겋게 물든다. 커밋 메시지는 반대로 72자에서 접어야 해서, 거기서는 예외를 명시했다.

## 나쁨/좋음 쌍

문서 작성 가이드 끝에는 예시를 붙였다. 앞의 규칙 전부가 한 번에 드러나는 문단을 골랐다.

````markdown
**나쁨: 예고 + 배경 나열 + 이력 + 동어 반복**

```markdown
## 4.3 리전 위반 탐지

이 섹션에서는 리전 위반 탐지 규칙에 대해 설명한다. 리전 위반 탐지란 허용되지 않은
리전에서 리소스가 생성되는 것을 탐지하기 위한 기능으로, 기본적으로 AWS Config 룰을
활용하여 구현하도록 하였다. 초기에는 허용할 타입을 나열하는 포함 목록 방식으로
설계하였으나, 검토 결과 제외 방식으로 전환하는 것이 타당한 것으로 판단되어
변경하였다. 즉, 허용 타입을 나열하는 대신 제외할 타입을 나열하는 방식이다.
```

**좋음: 결론 먼저, 지금 상태만**

```markdown
## 4.3 리전 위반 탐지

Config 룰이 비허용 17개 리전에서 리소스 생성을 탐지한다. 제외 목록 방식이라
새 리소스 타입이 생겨도 탐지 범위에 자동으로 들어온다.
```
````

다섯 줄이 두 줄이 됐는데 빠진 정보는 없다. 이 대비를 보여주는 쪽이 "간결하게 쓰라"는 지시보다 훨씬 잘 먹혔다.

# 주석 규칙은 숫자로

주석은 문서보다 다루기 쉬웠다. **줄 수 상한**이라는 명확한 기준을 줄 수 있어서다.

| 대상 | 최대 길이 |
| --- | --- |
| 변수·필드·상수 | **2줄** |
| 메서드·함수 | **5줄** |
| 히스토리(예외 허용 시) | **5줄** |

여기에 두 가지를 덧붙였다.

```markdown
- 코드만 봐도 자명한 내용은 주석을 아예 쓰지 않는다.
  (`// 캠페인 ID`를 `campaignId` 위에 붙이지 않는다.)
- 파라미터·반환값을 그대로 나열하는 형식적 JavaDoc은 쓰지 않는다.
  설명할 제약(단위, 범위, null 허용 여부, 예외)이 있을 때만 남긴다.
```

"형식적 JavaDoc을 쓰지 않는다"만으로는 부족했다. 그러면 주석을 아예 안 달아버린다. **무엇을 남겨야 하는지**(단위, 범위, null 허용 여부, 예외)까지 지목하고 나서야 남길 것과 지울 것이 갈렸다.

주석에서도 이력은 금지하되, 지우면 장애로 이어지는 경우는 예외로 뒀다.

```java
// 나쁨: 이력 + 자명한 설명
/**
 * 캠페인 예산 상한.
 * 2024-03 기획 변경으로 1000만원 -> 5000만원 상향 (김OO 요청).
 * 이전에는 CampaignPolicy에 있었으나 이쪽으로 옮김.
 */
private static final long MAX_BUDGET = 50_000_000L;

// 좋음: 코드에 없는 정보(단위)만
/** 캠페인 일일 예산 상한 (KRW). */
private static final long MAX_BUDGET = 50_000_000L;
```

```java
// 허용되는 히스토리 주석
// SSP 응답의 price 필드가 문자열로 오는 경우가 있어 방어 파싱한다.
// 파트너 스펙 수정 전까지 제거 금지.
```

# 파일을 나눈 이유

이걸 전부 `CLAUDE.md` 한 파일에 넣으면 몇백 줄이 된다. 그래서 층을 나눴다.

```
~/Projects/
├── CLAUDE.md                     # 전 작업 공통: 표기와 문장 규칙
└── guides/
    ├── document-writing.md       # 문서
    ├── code-comment.md           # 주석
    └── commit-message.md         # 커밋 메시지
```

`CLAUDE.md` 하단에서 `@` 경로로 불러온다.

```markdown
## 세부 지침

아래 문서를 따른다. (`@` 경로는 세션 시작 시 자동으로 함께 로드된다.)

- [문서 작성](guides/document-writing.md): @guides/document-writing.md
- [커밋 메시지 작성](guides/commit-message.md): @guides/commit-message.md
- [코드 주석 작성](guides/code-comment.md): @guides/code-comment.md
```

나눈 기준은 **적용 범위**다. 엠 대시 금지와 번역투 규칙은 모든 산출물에 걸리니 `CLAUDE.md`에 두고, 줄 수 상한이나 커밋 footer 규칙처럼 특정 산출물에만 걸리는 건 가이드로 뺐다. 그리고 가이드 안에서는 문장 규칙을 다시 쓰지 않고 참조만 한다.

```markdown
문장 단위 표현은 CLAUDE.md `표기와 문장 규칙`을 따른다.
```

문서 작성 가이드에 적은 "같은 사실을 두 곳에 쓰지 않는다"를 가이드 자신에게 적용한 셈이다. 양쪽에 써두면 한쪽만 고쳤을 때 규칙끼리 어긋난다.

또 하나, 이 파일들을 `~/Projects` 아래에 뒀다. 프로젝트마다 복사하면 열 군데에 같은 규칙이 흩어지고, 고칠 때마다 전부 따라다녀야 한다. 상위 디렉토리의 `CLAUDE.md`는 하위 프로젝트 세션에도 함께 로드되므로, 문체 규칙처럼 **어느 저장소에서 일하든 똑같이 적용될 규칙**은 위층에 두는 편이 낫다.

# 남은 것

완전히 해결되지는 않았다.

**긴 세션에서는 흐려진다.** 컨텍스트가 길어질수록 초반에 로드된 규칙의 영향력이 약해진다. 특히 대화가 영어 문서나 영어 로그로 채워진 뒤에 한국어 문서를 쓰게 하면 번역투가 다시 올라온다. 이럴 땐 그냥 다시 짚어주는 게 빠르다.

**치환표에 없는 표현은 못 잡는다.** 표에 있는 열두 개는 확실히 사라졌는데, 목록에 없는 새로운 번역투가 나오면 그대로 통과한다. 결국 눈에 띌 때마다 표에 한 줄씩 추가하는 식으로 유지하고 있다. 그래서 표로 만들어둔 게 편했다. 한 줄 추가로 끝난다.

**문서 종류에 따라 조정이 필요하다.** 지금 규칙은 기술 문서 기준이라 압축을 선호한다. 온보딩 문서나 외부 공유용 문서에는 좀 더 설명이 필요한데, 그럴 땐 그 세션에서만 예외를 말해주고 있다.

그래도 "간결하게 써줘"를 매번 입력하던 시절보다는 낫다. 회수되는 시간이 규칙을 정리하는 데 든 시간을 진작에 넘었다.

정리하면 이렇다. **AI에게 문체를 요구할 때는 형용사를 주지 말고 판정 기준을 준다.** "간결하게"가 아니라 "5줄 이내로", "자연스럽게"가 아니라 "이 표현은 저 표현으로". 그리고 규칙마다 나쁨/좋음 한 쌍을 붙인다. 이 세 가지가 문체 지시를 실제로 작동하게 만든 전부였다.
